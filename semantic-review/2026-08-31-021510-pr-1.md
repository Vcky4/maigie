# Durable Ask Maigie generation identity, retry, reconnect, and answer scope

This change gives each persisted learner message a durable generation history, records the exact answer scope on assistant rows, and teaches the web client to distinguish optimistic, message, and attempt identities. Retry regenerates an existing persisted turn, reconnect rehydrates history, and accessibility output announces state transitions instead of cumulative content. OpenAPI carries generation summaries and nullable historical scope through to the web mapper. **Watch for: confirmed — Stop can rehydrate before `CANCELLED` is committed; confirmed — a disconnect before `message_saved` leaves reconnect unable to correlate the persisted turn; confirmed — WebSocket authentication failure still has no verified refresh trigger or documented deployment check.**

**Verdict**: NEEDS_CHANGES

## High-level view

The normal identity path separates `tempId`, immutable `ChatMessage.id`, and `attemptId`; durable retry creates only a new attempt and does not replay text or attachments. Server-declared retryability is restored from history.

Reconnect is epoch- and sequence-guarded, skips the initial connection, and replaces persisted local state with server state. **Confirmed:** cancellation acknowledgement can precede its durable update, and losing the save acknowledgement leaves no server identity with which to reconcile the optimistic row.

Answer scope is derived once from enriched model context, persisted with the assistant, returned live, and exposed as nullable history. Legacy null rows make no claim, while recorded non-library answers explicitly state that whole-library recall was unavailable.

HTTP refresh is single-flight and refresh events reconnect the socket without stale callbacks winning. **Confirmed:** the backend rejects an invalid socket token with HTTP 403 during upgrade, but the browser client cannot observe that status and retries the stale token unless another HTTP request refreshes it.

<details><summary>Details</summary>

## Cancellation acknowledgement races durable retry state

**Confirmed:** the WebSocket loop calls `cancel_turn()` and immediately sends `event.stopped=true`; the generation task only later updates the attempt to `CANCELLED`. The store clears its active identities on that acknowledgement and immediately reads history. If the read wins, the server row maps back to `pending`; no post-commit terminal frame corrects it, so durable Retry remains unavailable until another history load.

Send the terminal acknowledgement after the durable transition or emit a second correlated terminal frame after commit. A test should hold the attempt update behind a barrier and prove the client eventually sees `stopped` plus `retryable=true` without reopening the conversation.

## Reconnect cannot recover a turn whose save acknowledgement was lost

**Confirmed:** reconnect identifies the active server learner row only through `activeUserMessageId` or `activeAttemptId`, both learned from `message_saved`. If persistence succeeds but that frame is lost, history may contain both learner and assistant rows while the client still has neither identity. The merge appends the temp row beside server history, leaves `clientTempId` active, and cannot accept later stream/final frames because `activeAttemptId` is null.

Use a durable correlation that survives this window, or a strict fallback that adopts the sole latest generation associated with the reconnecting turn. Current tests cover only the pure merge helper; store/socket tests should disconnect before `message_saved` and cover RUNNING and SUCCEEDED history.

## WebSocket authentication refresh remains externally undefined

**Confirmed:** invalid JWTs produce HTTP 403 during the WebSocket handshake. Avoiding refresh on generic socket errors is correct, but the client receives no typed auth frame or HTTP status; reconnect therefore uses the expired token until its retry limit unless unrelated HTTP traffic emits `token-refreshed`.

Record the required external check: verify the deployed proxy/browser close code and reason for a 403 handshake, or add a testable application-level auth close/frame. Only that verified signal should call `refreshAccessToken`; generic errors, 1006, and ordinary disconnects must not cause refresh storms.

## Exact scope and split identity contracts

One `AnswerScope` derived from the enriched context feeds `build_assistant_row`, `AskResponse`, and `assistant_final`. `complete_attempt` inserts the scoped assistant and marks success atomically, while migration 062 and the ORM keep old rows null. The UI attaches scope only to assistant messages, lists recorded sources, and makes the explicit no-whole-library statement when `libraryRecall=false`.

A normal save replaces the optimistic key with the persisted USER ID and separately installs the attempt ID for stream, final, error, and cancel correlation. Retry sends `{type:'retry', sessionId, messageId, tempId}` without content or attachments; the backend reuses the USER row only after checking ownership, terminal state, side effects, retryability, and absence of an answer. Pre-persistence failures remain a distinct “Send again” path.

## Event-based accessibility output

The polite live region announces listening, thinking, stream start, stop, copy, and final completion as transitions rather than reading an expanding prefix. Error text remains one alert and credit notices remain statuses. Focused tests cover single stream/final announcements and scope text.
