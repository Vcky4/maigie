# Lifecycle-safe Ask attempts and reloadable retry state

The lifecycle follow-up closes the five integration-critical races from the prior review: cancellation ends at provider/tool generation, live attempts renew a fenced lease, assistant persistence and success are atomic, mutating intent is durable before tool execution, and history exposes the latest generation state. Personalization fan-out is concurrent, aggregate-based, and bounded to two seconds, while focused race tests cover the new boundaries. Two prior hygiene findings remain, but neither blocks web/mobile from integrating the Ask, retry, and history contracts. **Watch for:** **confirmed, non-blocking:** two backend references still advertise the removed legacy chat endpoint; **confirmed, non-blocking:** broad formatting churn remains mixed into the lifecycle diff.

**Verdict**: APPROVED

## High-level view

Cancellation targets only provider generation and tool execution. Once generation returns, accounting and atomic completion continue despite Stop or socket disconnect; a Stop racing ahead of generation-task registration is retained and applied when generation starts.

A RUNNING attempt is heartbeated every 60 seconds under a database status fence, with stale expiry at five minutes. If expiry wins, the old worker cannot insert an assistant or rewrite the outcome; if completion wins, the assistant row and SUCCEEDED transition commit together.

All three provider adapters mark mutating intent before handlers start, and marker failure prevents execution. This favors duplicate prevention over automatic retry: a failed attempt becomes non-retryable once a mutating tool is about to run.

History adds a camelCase `generation` summary to USER messages with `latestAttemptId`, status, retryability, and failure code. Web and mobile can reconstruct failed/cancelled state and retry after reload without relying on transient socket frames.

Of the nine earlier findings, items 1–6 and 9 are addressed. Item 7 remains in two stale backend documents and item 8 remains as review/merge noise; neither changes the client contract.

## Fenced lease ownership across generation and completion

The lease establishes ownership before work and renews `updatedAt` every 60 seconds. Stale expiry changes only PENDING/RUNNING rows older than five minutes, and outcome-changing writes are fenced by `status = RUNNING`. A worker whose attempt expired cannot complete or later rewrite the row; `complete_attempt` rolls back the assistant insertion when its fenced update affects no row.

Completion inserts the ASSISTANT message and transitions the attempt to SUCCEEDED in one transaction. The heartbeat accepts the just-committed SUCCEEDED state during context shutdown. This closes prior findings 2 and 3 without another answer/attempt consistency window.

## Stop is confined to provider and tool generation

`answer()` registers only its dedicated generation task as cancellable. Charging, action logging, outcome preparation, and atomic completion run after that registry closes, so a late Stop cannot cancel persistence. The pending-cancellation set covers the interval between `message_saved` and generation-task registration, and terminal cleanup clears it.

Stop can still cancel an in-flight tool handler, but mutating intent is already persisted and the repository prevents cancellation handling from restoring `retryable=true`. This closes prior finding 1 and the unsafe-retry portion of finding 4.

## Mutating intent precedes every provider handler

OpenAI marks each selected tool immediately before its handler; Gemini and Anthropic mark the full batch before starting independent or dependent handlers. The shared classifier covers every registered mutating tool: `create_*` plus note mutation, review completion, course update/deletion, fact saving, email, schedule regeneration, document generation, resource recommendation, and topic completion. Marker persistence failure propagates outside the handler catch, so no mutation starts when retry safety cannot be recorded.

The marker is conservative rather than transactional idempotency. A handler that fails before writing still leaves the attempt non-retryable, requiring a new learner turn, but ambiguous crashes cannot trigger duplicate writes through Retry.

## Reloaded history carries retry decisions

History selects the latest attempt per USER message with a window function and joins it into the paginated query. The response serializes `generation.latestAttemptId`, `generation.status`, `generation.retryable`, and `generation.failureCode`; a model-validation smoke test confirmed the camelCase wire shape.

This closes prior finding 5. A reopened client has the message ID and latest attempt state needed to render FAILED or CANCELLED and call the owner-scoped retry endpoint.

## Bounded personalization avoids serial full-card reads

Profile, behaviour, flashcard statistics, contextual entity, and space-membership reads run concurrently under a two-second timeout. Due-card context uses aggregate statistics instead of loading 101 records. Enrichment failure removes unverified client-supplied entity IDs and continues without optional personalization, closing prior finding 6 while preserving fail-closed ownership.
