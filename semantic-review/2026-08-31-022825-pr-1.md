# Durable Ask Maigie turns now reconcile across retry, cancellation, and reconnect

This change persists the exact answer scope with each new assistant message and exposes durable generation state through conversation history. The web client now keeps optimistic turn IDs, persisted learner-message IDs, and generation-attempt IDs separate, using the latter for stream/cancel correlation and the persisted learner ID for retry. Retry reuses the immutable server turn, while reconnect performs an authoritative guarded merge and can recover both delayed cancellation state and a uniquely identifiable lost save acknowledgement. **Watch for: no remaining task-related behavioral blocker was found in this follow-up pass.**

**Verdict**: APPROVED

## High-level view

Answer scope is derived from the enriched context actually supplied to generation, stored on the assistant row, and returned consistently in live and historical responses. Historical rows remain nullable, so the UI makes no provenance claim where none was recorded.

Generation attempts form the durable lifecycle around each persisted learner message. Live frames and cancellation use the attempt identity; updates and retries use the learner-message identity; server history restores status, retryability, and failure codes after reload.

Reconnect rehydrates only after a real disconnect/reconnect and guards each read by session, conversation epoch, and rehydrate sequence. A cancellation acknowledgement starts a bounded poll for that exact attempt, while a missing `message_saved` acknowledgement can adopt only one recent learner row with exact text, image ordering, and a generation identity; ambiguous matches are refused.

The browser socket still refreshes only on the existing token-refresh event because the backend's HTTP 403 upgrade rejection is not observable as a typed browser WebSocket status. The client documents the exact production proxy/browser close-code and reason check required before wiring the exported single-flight refresh primitive, avoiding refresh storms based on guessed signals.

## Correlated cancellation and lost-ack recovery

The cancellation acknowledgement can arrive before the backend transaction records `CANCELLED`, so the client retains the acknowledged attempt ID long enough to poll history up to five times. Each read locates the learner row by that attempt, stops as soon as generation becomes terminal, and is discarded if the conversation epoch, session, or rehydrate sequence changed meanwhile.

The lost-save fallback handles the narrower disconnect window where persistence succeeded but the connection-specific acknowledgement did not arrive. Adoption requires a learner row with a generation attempt, exact content and ordered image URLs, a timestamp no older than five minutes before the optimistic turn, and exactly one match. A completed recovered turn drops the optimistic row and stale stream; an active recovered turn installs its persisted message and attempt identities for subsequent correlation.

## Immutable durable retry identity

A retry frame carries only `{type:'retry', sessionId, messageId, tempId}`. The backend resolves the owned persisted learner row and latest attempt, rejects non-terminal, non-retryable, side-effecting, or already-answered turns, restores persisted images, and creates a new attempt without another learner bubble. Local upload or pre-persistence failures remain visibly separate as “Send again” and use the normal send path.

## Exact answer scope across live and historical answers

Migration 062 adds nullable JSONB scope to `ChatMessage`; ORM mapping and assistant-row construction preserve the same derived scope used by `AskResponse` and `assistant_final`. Conversation history exposes that value only on assistant rows. Rendering lists recorded sources and explicitly says the whole library was not searched when `libraryRecall=false`, while null historical scope renders nothing.

## Event-based announcements and authentication boundary

The live region announces state transitions instead of replaying the growing stream, emits completion once for a new assistant ID, and leaves errors to the existing alert and credit information to its status region. Stop and copy are concise events rather than message-content announcements.

Socket refresh reuses the HTTP client's exported single-flight primitive indirectly through `token-refreshed`, and stale socket callbacks are identity-guarded. Invalid upgrade credentials are rejected by the backend with HTTP 403, but generic browser socket errors are intentionally not treated as authentication failures; the source records the production proxy/browser signal that must be verified before adding a direct refresh trigger.
