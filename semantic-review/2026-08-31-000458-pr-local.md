# Durable Ask attempts, retry, cancellation, and owned learner context

This change adds durable generation-attempt rows, cross-worker exclusion, HTTP and WebSocket retry paths, attempt-attributed LLM costs, and broader owner-scoped learner context. It also removes the dead personal-learning chat shim and carries attempt IDs through the public Ask response and socket acknowledgement. The happy paths and ownership checks are covered, but the lifecycle is unsafe at its timing boundaries and persisted retry is not discoverable after reload. **Watch for:** **confirmed** cancellation can interrupt charging/persistence after generation; **confirmed** the unrefreshed five-minute lease permits overlapping attempts; **confirmed** a stored answer can be reported as failed when the terminal update fails; **confirmed** retry state is absent from history; **confirmed** committed tool mutations have a crash window before the safety marker is durable.

**Verdict**: NEEDS_CHANGES

## High-level view

A `ChatGenerationAttempt` now anchors a learner message, generation status, retry decision, assistant result, and provider cost. A partial unique index gives the database authority over one active attempt per conversation, while the existing in-process guard remains the fast path.

Cancellation and stale-attempt recovery undermine that authority at the edges. The cancellable task includes post-generation accounting and persistence, and the fixed lease can expire a healthy long-running request because no heartbeat advances `updatedAt`.

Retries reuse the original USER row, image URLs, and context, then re-run ownership-aware enrichment. The write path is available over HTTP and WebSocket, but conversation history does not return attempt state, so a reopened thread cannot show failure or determine whether retry is allowed.

Context enrichment now verifies exam-prep, study-plan, goal, reflection, and space IDs before using them and strips unverified IDs on failure. It also adds several synchronous reads to every Ask turn, including turns with no contextual IDs.

The semantic change is mixed with broad formatter churn across a 3,000-line route module, ORM models, provider adapters, and tests. The legacy route removal is intentional according to the integration plan, but backend feature documentation still advertises it.

<details><summary>Details</summary>

## Stop remains active through charging and answer persistence

**Confirmed:** `websocket_handler.py` registers the entire `ask_service.answer()` task with `cancellable_turn`, while `answer()` continues after provider generation through action-log writes, queued work, credit consumption, assistant-message creation, and the terminal attempt update. A cancel frame can therefore land after the provider has finished. Depending on the await point, the learner can be charged without an assistant row, receive a cancelled acknowledgement while an assistant row exists, or have a completed tool mutation followed by a cancelled attempt.

This contradicts the nearby comment that the stoppable window closes once generation produces the answer. Narrow cancellation to the provider/tool-generation phase, then make accounting, assistant persistence, and terminal transition a shielded completion path with an explicit result.

## The five-minute active-attempt lease can expire a live turn

**Confirmed:** `_expire_stale_attempts()` changes every `PENDING` or `RUNNING` attempt older than 300 seconds to `FAILED`, and runs immediately before creating a competitor. No heartbeat or phase update refreshes `updatedAt` while the provider, tools, or post-processing run. A legitimate turn exceeding five minutes can be declared dead; the partial unique index then admits a second attempt while the first worker continues.

That permits duplicate provider spend, answers, and tool mutations. Refresh the lease while work is live or use a fencing token/owner lease that prevents an expired worker from committing after a replacement starts; derive the timeout from the real maximum provider/tool duration.

## Answer persistence and terminal attempt state are split commits

**Confirmed:** `answer()` writes the assistant `ChatMessage` and only afterward calls `update_attempt(... SUCCEEDED ...)` in a separate transaction. If that update fails, HTTP and WebSocket treat the call as generation failure even though the answer may be stored and credits consumed. The generic handler can mark the attempt `FAILED`; retry is blocked only later by a separate `user_message_has_answer()` query, after the client was told no answer was produced.

Persist the assistant row and successful terminal transition atomically, or recover terminal-state failure without converting a committed answer into a failed response. The same transaction should establish the reply link used by retry exclusion.

## Side-effect safety is recorded after the mutation commits

**Confirmed:** all three provider adapters await `handle_tool_call()` before invoking `progress_callback(... tool_side_effect=True)`, which performs the durable `toolSideEffects` update. A crash or cancellation between the tool commit and callback leaves a failed/stale attempt marked side-effect-free and eligible for retry. Classification after execution cannot close this window.

Mark mutation intent before invocation and make handlers idempotent under an attempt-scoped key, or commit the mutation and marker in the same transaction. Without that, `toolSideEffects = false` does not prove retry safety.

## Persisted retries are not represented in conversation history

**Confirmed:** `ChatMessageResponse` has no attempt ID, status, failure code, or retryability, and history does not join attempts. The retry endpoint requires `session_id` and `message_id`, but after reload clients receive only USER and ASSISTANT rows and cannot distinguish a failed unanswered turn from a legacy message or determine whether the latest attempt is retryable. WebSocket errors expose retryability only on the live connection.

Expose the latest attempt summary alongside each USER message or add an owner-scoped attempt/status endpoint. Web and mobile need enough state to render failed/cancelled turns and retry after reconnect without guessing.

## Owner-scoped personalization adds unconditional turn latency

**Confirmed:** removing the early return for empty context means every turn reads the learner profile, behaviour profile, and up to 101 due flashcards before generation; entity reads are additional. These calls are sequential inside `_read_learner_context`, outside the context cache, and run for plain questions with no context IDs.

Preserve the ownership checks, but fetch independent data in parallel, replace loading 101 rows with a count query, and add a bounded timeout/cache so optional personalization cannot dominate first-token latency.

## Legacy route removal leaves backend references behind

**Confirmed:** deleting `POST /api/v1/learning/chat` and `chat_helper.py` matches the cross-client integration plan. However, `src/domains/personal_learning/FEATURE_REGISTRY.md`, `docs/PERSONAL_LEARNING_USER_FLOW.md`, and `tests/PERSONAL_LEARNING_TEST_PLAN.md` still advertise that endpoint, directing implementation and manual verification toward a 404.

Update those references with `POST /api/v1/intelligence/ask` and `WS /api/v1/intelligence/ws`.

## Formatter churn obscures the integration-critical delta

**Confirmed:** the diff reformats hundreds of unrelated lines in `personal_learning/routes.py`, `db_models.py`, provider adapters, and tests; the personal-learning route alone changes 456 lines to remove one endpoint. The new ownership test is also untracked while no conversation-service source line changes in this working diff. This materially complicates lifecycle/security review and raises merge-conflict risk before coordinated web/mobile work.

Split or revert formatting-only changes and retain the route deletion, lifecycle, ownership enrichment, migration, generated OpenAPI, and direct tests as a focused diff.

## Lifecycle race coverage is missing

**Confirmed:** the focused Ask/socket/context/cost/routing suite passes 219 tests; schema/import coverage passes 822 tests with 6 expected failures; Ruff passes. No test drives a cancel between generation and persistence, a live attempt beyond the lease, a failed terminal update after assistant persistence, a crash between tool commit and marker, or retry discovery after history reload. Add deterministic tests for these state-machine boundaries before client integration.
